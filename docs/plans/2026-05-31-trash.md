# Исправление: удаление задач из корзины

**Дата:** 2026-05-31
**Статус:** План (v3, утверждён)

## Описание проблемы

Задачи в корзине не удаляются корректно. При нажатии "Очистить корзину" задачи исчезают, но периодически появляются снова.

## Корневая причина

`Trash.tsx:confirmClearTrash` создаёт индивидуальные `delete`-мутации для каждой задачи вместо вызова бэкенд-эндпоинта `DELETE /tasks/trash/clear`. Это приводит к:

1. **Rate limiting** — N задач = N HTTP-запросов `DELETE /tasks/{id}`. Лимит 20/мин (`backend/app/config.py:28`). При >20 задачах часть запросов получает 429.
2. **429 не обрабатывается** — в `syncEngine.ts` нет обработки 429, мутация остаётся в очереди. После 10 неудач — discard.
3. **Re-download при pull** — после discard мутации и физического удаления локальной записи, pull загружает задачу с сервера (она всё ещё там). Проверка `_syncStatus === 'deleted'` в `mergeAndPut` не срабатывает, т.к. `localRecord === undefined` (физически удалена).

## План исправления

### 1. `frontend/src/routes/Trash.tsx` — переписать `confirmClearTrash`

**Было:** цикл из N мутаций `delete` + `_syncStatus: 'deleted'`
**Стало:**

- Собрать ID задач: `db.tasks.where('[userId+gtdStatus]').equals([user.id, 'trash']).filter(t => t._syncStatus !== 'deleted').toArray()` → `trashIds`
- Попробовать `httpClient.delete('/tasks/trash/clear')`

**При успехе API (200):**
- `db.tasks.bulkDelete(trashIds)` — физическое удаление
- Удалить все pending-мутации для trash-задач: `db.mutations.where('[entityType+entityId]')` для каждого trashId → `delete()`
- Обновить UI через `setRefreshKey`

**При ошибке (нет сети, 500, timeout):**
- Не удалять старые pending-мутации — `deduplicateMutations` разберётся
- Fallback: для каждой задачи установить `_syncStatus: 'deleted'` и создать `delete`-мутацию
- Задачи исчезнут из UI, удалятся при следующем push
- Показать toast с предупреждением «будет синхронизировано позже»

### 2. `frontend/src/routes/Completed.tsx` — переписать `handleConfirm2`

Аналогично пункту 1:
- `httpClient.delete('/tasks/completed/clear')` с fallback на мутации при ошибке
- При успехе: `bulkDelete` + удалить pending-мутации
- При ошибке: fallback (старые мутации не трогать, создать новые `delete`-мутации)

### 3. `frontend/src/db/syncEngine.ts` — tombstone cache в `mergeAndPut`

- Добавить модульный `Set<string>` для кэша tombstone ID
- В `processTombstones()`: добавлять `${entityType}:${entityId}` в кэш при обработке каждого tombstone
- В `mergeAndPut()`: если ID в кэше → `continue` (пропустить)
- Очищать кэш в начале каждого `pull()` / `initialSyncInternal()`

Защищает от re-download задач, удалённых на сервере, но чьи локальные записи уже физически удалены.

### 4. `frontend/src/db/syncEngine.ts` — `processTombstones` в `initialSyncInternal`

`initialSyncInternal` (строки 324-332) не вызывает `processTombstones`. Без этого при начальной синхронизации (обновление страницы, новый вход) tombstones не обрабатываются, и удалённые на сервере записи могут быть re-скачаны через `mergeAndPut`.

Добавить вызов `processTombstones()` ДО `mergeAndPut` в `initialSyncInternal`.

### 5. `frontend/src/db/syncEngine.ts` — обработка 429 в `executeMutationGroup`

В блоке `if (err instanceof ApiError)` добавить перед проверкой `err.status >= 500`:

```typescript
if (err.status === 429) {
  if (attempt < 2) {
    await sleep(5000 * Math.pow(2, attempt))
    continue
  }
  await db.mutations.update(mutation.id, {
    retryCount: mutation.retryCount + 1,
    lastError: err.message,
  })
  break
}
```

429 — не ошибка данных, сервер просит подождать. Первые 3 попытки (attempt 0, 1, 2) не считаются за failed.

### 6. SSE `tasks_cleared` — без изменений

Текущая обработка в `SyncProvider.tsx:67` уже делает полный `pull()` для `tasks_cleared`, что корректно: `processTombstones` очистит оставшиеся локальные записи. Безопасный fallback.
