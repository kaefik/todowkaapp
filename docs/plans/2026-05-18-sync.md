**Дата**: 2026-05-18
**Статус**: В работе

## Описание проблемы

При использовании нескольких экземпляров фронтенда (несколько вкладок, устройств) наблюдаются:
1. Завершённые задачи «возвращаются» как активные
2. Задвоение задач
3. Удалённые задачи продолжают отображаться

---

## Найденные баги

### BUG #1 (КРИТИЧЕСКИЙ): Гонка между push и pull

**Файлы**: `frontend/src/components/SyncProvider.tsx`, `frontend/src/db/conflictResolution.ts`

Push и pull выполняются параллельно без mutual exclusion. Pull может получить устаревшие данные с сервера ДО того, как push доходит до сервера. После успешного push локальная запись получает `_syncStatus: 'synced'`, и последующий merge перезаписывает её устаревшими данными из pull.

**Сценарий:**
```
T0:   Пользователь toggle (complete) → local: completed, _syncStatus: modified
T1:   Periodic pull → сервер ещё не получил toggle → возвращает UNCOMPLETED
T1.5: Push выполняется → сервер теперь COMPLETED
T1.6: Push OK → local _syncStatus: 'synced', mutation удалена
T1.7: Pull merge → shouldSkipMerge (нет pending mutations) → proceed
T1.8: mergeRecord: local 'synced' → return serverRecord (STALE из T1)
T2:   bulkPut перезаписывает → задача снова UNCOMPLETED
```

### BUG #2 (КРИТИЧЕСКИЙ): Удалённые сущности не синхронизируются между клиентами

**Файлы**: `backend/app/api/tasks.py:31-36`, `frontend/src/components/SyncProvider.tsx:109`, `frontend/src/db/syncEngine.ts:375-382`

Три проблемы складываются вместе:

1. **`pull()` не вызывает `removeServerDeleted()`** — только `initialSync()` (при логине) чистит удалённые записи. `removeServerDeleted` нельзя добавить в `pull()` с `updated_since`, потому что сервер возвращает только ИЗМЕНЁННЫЕ записи, а функция сравнивает serverIds со ВСЕМИ локальными.

2. **Бэкенд публикует ВСЕ task-события как `task_updated`** — включая `action: "deleted"`. Фронтенд проверяет `evt.endsWith('_deleted')`, что всегда `false` для `task_updated`.

3. **Нет tombstone** — сервер делает hard delete для ВСЕХ сущностей (задачи, проекты, области, контексты, теги, календарные события, чеклисты). После удаления сервер не может сказать «эта запись была удалена». Удаления проектов/областей/контекстов/тегов работают через SSE (`project_deleted` и т.д.), но если SSE пропущено — запись «зависает» навсегда, как и для задач. Удаления `calendarEvent` и `checklistItem` подвержены той же проблеме: `calendar_event_deleted` публикуется через SSE, но при пропущенном событии запись «зависает» навсегда.

### BUG #3 (СРЕДНИЙ): Дедупликация toggle + state-flipping сервер

**Файлы**: `frontend/src/db/syncEngine.ts:489-493`, `backend/app/services/task_service.py:386-443`

Быстрый double-toggle (complete → uncomplete) дедуплицируется в один toggle. Серверный toggle делает `is_completed = not is_completed` (инверсия текущего состояния). Если первый toggle не дошёл, сервер инвертирует из неправильного состояния.

### BUG #4 (НИЗКИЙ): Хрупкий парсинг entityId из SSE

**Файл**: `frontend/src/components/SyncProvider.tsx:113-116`

Для `checklist_updated` парсит `data.checklist_id`, но сервер отправляет `{"task_id": "..."}`. EntityId = undefined. `isPushEcho` проверяет ЛЮБОЙ push echo для checklistItem.

#### Шаг 1.1: Promise-based mutex для push и pull

**Файл**: `frontend/src/components/SyncProvider.tsx`

Заменить `pushingRefGlobal` / `pullingRefGlobal` флаги на Promise-based mutex с таймаутом. Push, pull и selectivePull никогда не выполняются параллельно.

```typescript
class Mutex {
  private queue: Promise<void> = Promise.resolve()

  async runExclusive<T>(fn: () => Promise<T>, timeoutMs = 60000): Promise<T> {
    let release: () => void
    const prev = this.queue
    this.queue = new Promise<void>(resolve => { release = resolve })

    await prev  // ждём освобождения мьютекса (без таймаута — иначе можем никогда не получить блокировку)

    try {
      // Таймаут на ВЫПОЛНЕНИЕ функции, не на ожидание
      // 60s — pull может fetchAllPages для 8 ресурсов при медленном соединении
      return await Promise.race([
        fn(),
        new Promise<never>((_, reject) =>
          setTimeout(() => reject(new Error('Mutex execution timeout')), timeoutMs)
        )
      ])
    } finally {
      release!()
    }
  }
}

const syncMutex = new Mutex()
```

Использование — обернуть ВСЕ синхронные операции (schedulePush, schedulePull, doPush, doPull):
```typescript
function schedulePush() {

  pushTimer = setTimeout(() => {
    syncMutex.runExclusive(async () => {
      updateSyncing(true)
      try {
        await push()
        setLastSyncAtFn?.(new Date())
      } finally {
        updateSyncing(false)
      }
    })
  }, PUSH_DEBOUNCE_MS)
}

function schedulePull(userId: string, eventType?: string) {
  if (pullTimer) clearTimeout(pullTimer)
  pullTimer = setTimeout(() => {
    syncMutex.runExclusive(async () => {
      updateSyncing(true)
      try {
        if (eventType) {
          const resourceType = getResourceTypeFromSSE(eventType)
          if (resourceType) {
            if (eventType === 'task_updated' || eventType === 'task_deleted' || eventType === 'tasks_cleared') {
              await pull(userId)
            } else {
              await selectivePull(userId, [resourceType])
            }
          } else {
            await pull(userId)
          }
        } else {
          await pull(userId)
        }
        setLastSyncAtFn?.(new Date())
      } finally {
        updateSyncing(false)
      }
    })
  }, PULL_DEBOUNCE_MS)
}
```

Обернуть начальные doPush/doPull в mutex (вызываются при монтировании SyncProvider):

Централизованный сервис для записи tombstone. Все delete-операции во всех API endpoints вызывают его.

```python
class DeletionService:
    def __init__(self, db: AsyncSession):
        self.db = db

    async def record_tombstone(self, user_id: str, entity_type: str, entity_id: str):
        self.db.add(DeletedEntity(
            user_id=str(user_id),
            entity_type=entity_type,
            entity_id=str(entity_id),
        ))

    async def record_tombstones_batch(self, user_id: str, entity_type: str, entity_ids: list[str]):
        records = [
            DeletedEntity(user_id=str(user_id), entity_type=entity_type, entity_id=str(eid))
            for eid in entity_ids
        ]
        self.db.add_all(records)

    async def get_deleted(self, user_id: str, since: datetime | None = None, entity_type: str | None = None) -> list[DeletedEntity]:
        stmt = select(DeletedEntity).where(DeletedEntity.user_id == str(user_id))
        if since:
            stmt = stmt.where(DeletedEntity.deleted_at >= since)
        if entity_type:
            stmt = stmt.where(DeletedEntity.entity_type == entity_type)
        result = await self.db.execute(stmt.order_by(DeletedEntity.deleted_at))
        return list(result.scalars().all())

    async def cleanup_old(self, days: int = 30):
        cutoff = datetime.now(UTC) - timedelta(days=days)
        await self.db.execute(
            delete(DeletedEntity).where(DeletedEntity.deleted_at < cutoff)
        )
        await self.db.flush()
```

#### Шаг 1.3: Обработка tombstone на фронтенде

**Файл**: `frontend/src/db/syncEngine.ts`

Добавить функцию `processTombstones`:

```typescript
async function processTombstones(userId: string): Promise<void> {
  const since = (await db.syncMeta.get('lastPullAt'))?.value ?? null
  if (!since) return  // Пропускаем при первом pull — initialSync сам чистит через removeServerDeleted

  let url = `/deleted?since=${encodeURIComponent(since)}`
  const response = await httpClient.get<{
    items: Array<{ entity_type: string; entity_id: string }>
  }>(url)

  if (!response.data.items.length) return

  const byTable = new Map<typeof db.tasks, string[]>()
  for (const item of response.data.items) {
    const table = getTableForType(item.entity_type as EntityType)
    if (!table) continue
    const existing = byTable.get(table) ?? []
    existing.push(item.entity_id)
    byTable.set(table, existing)
  }

  for (const [table, ids] of byTable) {
    await table.bulkDelete(ids).catch(() => {})
  }
}
```

Ключевые моменты:
- **Пропускаем при `since === null`** — `initialSync` уже обрабатывает через `removeServerDeleted`
- **Группируем по таблицам** — используем `bulkDelete` вместо 200 отдельных delete
- **Resilient** — ошибки не прерывают pull

Вызывать в `pull()` (но НЕ в `initialSync`):
```typescript
export async function pull(userId: string): Promise<void> {
  const since = (await db.syncMeta.get('lastPullAt'))?.value ?? null
  try {
    await processTombstones(userId)
  } catch (err) {
    console.warn('[SyncEngine] Tombstone processing failed, continuing pull:', err)
  }
  await Promise.all(RESOURCES.map(async (resource) => {
    const items = await fetchAllPages(resource.endpoint, since)
    await mergeAndPut(resource.table, resource.entityType, items, userId, resource.transform)
  }))
  await db.syncMeta.put({ key: 'lastPullAt', value: new Date().toISOString() })
}
```

### Ручные сценарии

1. **Две вкладки, toggle**: вкладка A → toggle complete → вкладка B показывает completed. Обновить B — задача остаётся completed.
2. **Две вкладки, delete**: вкладка A → удалить задачу → вкладка B перестаёт показывать задачу.
3. **Offline toggle**: toggle offline → выйти онлайн → задача корректно синхронизируется.
4. **Rapid double-toggle**: быстро toggle дважды → финальное состояние корректно.
5. **Clear completed**: очистить выполненные → все вкладки перестают показывать выполненные задачи.
6. **Delete project**: удалить проект на вкладке A → вкладка B перестаёт показывать проект.
7. **Delete calendar event**: удалить событие на вкладке A → вкладка B перестаёт показывать событие (даже если SSE пропущено).
8. **Delete checklist item**: удалить пункт чеклиста на вкладке A → вкладка B перестаёт показывать пункт.

## Ожидаемый результат

После исправления:
- Завершённые задачи больше не «возвращаются» (BUG #1 — mutex для push, pull, selectivePull)
- Удалённые задачи и другие сущности (включая calendarEvent, checklistItem) корректно удаляются на всех устройствах (BUG #2 — tombstone для ВСЕХ типов + SSE)
- Быстрый double-toggle работает корректно (BUG #3 — explicit state)
- SSE-события надёжно обрабатываются, включая calendar_event_* (BUG #4 — правильный парсинг + полные подписки)

**Примечание по httpClient**: httpClient фронтенда автоматически добавляет `/api` prefix ко всем endpoint-ам. Вызов `httpClient.get('/deleted?since=...')` резолвится в `/api/deleted?since=...`, что соответствует маршруту `deleted_router` внутри `api_router` (prefix="/api").
